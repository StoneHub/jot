# Evaluate Jev for Jot decisions

Status: exploration proposal, 2026-09-26. No Jot runtime integration or TypeSafe request is authorized by this document. Related: [field drafting issue #90](https://github.com/StoneHub/jot/issues/90).

## Recommendation

Keep AppleFM as Jot's local text generator. Jev is TypeSafe's hosted System One decision model: it answers bounded Choice, Noul (yes probability), and Score questions; it does not generate the user's draft. Do not put Jev inside the `AppleFM` library or add a Swift Jev framework now. If a measured Jot use case eventually warrants runtime use, keep a narrow optional decision adapter at the Jot application boundary. Jot should own the rubric, confidence policy, input bounds, cancellation, consent, and fallback. `AppleFMClient` should continue to own only on-device Foundation Models generation.

Jev could later help with ambiguous source relevance, whether a blank field has enough associated intent to draft, or semantic review of an AppleFM draft. It should not decide capture state, permissions, field identity, secure-field eligibility, source freshness, exact selection, insertion, or whether to send or execute text. Those remain deterministic Jot rules. The tab organizer's Jev gateway is evidence of a working HTTP pattern, not a reusable Jot API: its input schema, category rubric, browser consent, and Node server are specific to tabs.

## Current boundary and evidence

Jot's `SuggestionCoordinator` runs only after double-Fn, selects bounded local context, calls `AppleFMGeneration` through `ModelCallGate`, processes and reviews the text, and revalidates the field and sources before Tab insertion. `SuggestionPrompt` owns the prompt. `AppleFMClient` creates a fresh local session; the caller owns deadlines, limits, and validation. The current v4 synthetic evaluation completed 54 normal and 54 oracle records, but human quality scores are absent. It found repeated draft echoes, selected-range duplication, and lost constraints. Its measured warm AppleFM generation median was about 420 ms, with p95 about 1.03 seconds. These are Jot measurements, not Jev measurements.

Jev accepts structured `state` and typed questions at `POST /v1/systemone` and returns probabilities. TypeSafe documents Python and JavaScript SDKs and a language-neutral HTTP API; no Swift SDK is listed as of this review. TypeSafe's published 70–500 ms latency and $0.042 per million input tokens are provider claims, not measurements on this Mac or a Jot workload. Costs include any gateway operations and change with actual token usage and account terms. The model's constrained output shape does not make its judgment correct. TypeSafe itself notes literal readings, weak counting/date reasoning, context distraction, prompt-injection susceptibility, and lack of text generation in Jev 1.13.

Privacy is a product boundary. AppleFM stays on device; Jev would send whatever Jot supplies to TypeSafe over the network. Field text, on-screen conversation, and transcripts can be sensitive even when bounded. TypeSafe's agreement says customer data is not put in a model-weight training dataset without prior consent, while allowing service processing and telemetry. This is different from an on-device guarantee. An embedded API key is unacceptable; any later product path needs explicit per-use consent, a secured user-controlled gateway or comparable credential design, a clear data policy, and local behavior on offline, timeout, refusal, or quota errors. None of those prerequisites should be bypassed for this evaluation.

## One bounded experiment

Test Jev **outside the app** as a possible semantic quality gate for draft output. Use only public synthetic Jot cases from `docs/evaluation/contextual-suggestions/` and new synthetic variants; send no personal transcript, field contents, credentials, or hidden application context. No app change, dependency, or installed build is needed.

1. Prepare at least 60 distinct synthetic candidate drafts, balanced between useful drafts and one clear defect each: plain echo, copying text outside the selected range, invented commitment, or dropped explicit constraint. Include untrusted quoted instructions. Human reviewers label each candidate's accept/reject result before Jev output is examined. Keep exact-number and literal echo checks in code.
2. Record the present deterministic `SuggestionOutput.process` and `.review` decisions as the baseline. Give Jev only the short seed, selected-range surroundings when relevant, and candidate. Ask one narrow Noul per semantic defect, such as whether the candidate contradicts or omits an explicit user constraint; do not ask it to rewrite. Pre-register the rubric and threshold using a development split, then score a held-out split. Record the returned model revision, request size, per-call latency, token usage, and error rate. A TypeSafe key and a separate decision to spend credits are prerequisites for live calls; without them, stop at the corpus and baseline.
3. Compare false accepts of defective drafts and false rejects of useful drafts with the baseline, including an offline/error fallback. Do not use repeated greedy AppleFM outputs as independent examples. Do not tune the held-out set after reading Jev decisions.

Consider a Jot runtime proof only if Jev catches at least 90% of held-out semantic defects that the baseline misses, falsely rejects no more than 5% of useful drafts, and has measured p95 added decision latency at or below 500 ms with reliable timeout behavior. These are experiment gates, not a claim of current accuracy. Even a passing experiment only justifies proposing a separately approved, opt-in runtime design; it does not authorize sending user data, adding a dependency, or building a general Swift framework. A failing or inconclusive result closes this idea for the current Jot suggestion flow and leaves issue #90's local prompt/output repair as the priority.
